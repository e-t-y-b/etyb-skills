## What it is

Cloud Storage for Firebase is Google Cloud Storage with Firebase Authentication and Security Rules layered on top. Buckets, objects, signed URLs — but with `request.auth` available in rules and client SDKs that handle resumable uploads, download URL generation, and progress monitoring.

Canonical reference: [Cloud Storage for Firebase docs](https://firebase.google.com/docs/storage).

## When to use it

**Use Cloud Storage for Firebase when:**

- You need to store user-generated content (images, audio, video, documents)
- You want Security Rules enforcement based on `request.auth`
- You want client SDKs that handle resumable uploads
- You want Cloud Functions `onObjectFinalized` to react to new uploads

**Use plain GCS directly when:**

- You need bucket-level features Firebase doesn't expose (lifecycle policies UI, advanced retention)
- The data is server-only — no client-facing uploads
- You're already using GCS for other workloads and unified IAM is preferred

## 2025-2026 currency anchors

Stable product. Notable historical context:
- **CORS configuration** is still applied via `gsutil cors set` on the bucket — Firebase Console doesn't expose CORS editing. CORS misconfig is the most common Storage bug.
- **`getDownloadURL()` produces long-lived public URLs** — un-revocable without deleting and regenerating the token. Prefer signed URLs for sensitive content.

## Patterns

### Server-signed upload URLs

```ts
import { getStorage } from "firebase-admin/storage";

const bucket = getStorage().bucket();
const [signedUrl] = await bucket.file(`uploads/${objectId}`).getSignedUrl({
  action: "write",
  expires: Date.now() + 15 * 60 * 1000,
  contentType: "image/png",
});
return { uploadUrl: signedUrl };
```

Standard pattern: "let a client upload directly to Storage without the bytes flowing through Cloud Functions." Apply Storage Security Rules to enforce path and metadata constraints. Run a Cloud Function on `onObjectFinalized` to scan/transcode/extract metadata after upload — **never trust client-asserted metadata**.

### Storage Security Rules

```javascript
rules_version = '2';
service firebase.storage {
  match /b/{bucket}/o {
    match /users/{userId}/{allPaths=**} {
      allow read:  if request.auth != null && request.auth.uid == userId;
      allow write: if request.auth != null && request.auth.uid == userId
                   && request.resource.size < 5 * 1024 * 1024
                   && request.resource.contentType.matches('image/.*');
    }

    match /public/{file} {
      allow read: if true;
      allow write: if false;
    }

    match /{path=**} {
      allow read, write: if false;
    }
  }
}
```

**Always size-bound uploads in rules.** Without a size cap, a client can upload 10 GB and run up your bill. The Storage SDK respects rules-level size limits and rejects oversize uploads before bytes flow.

**Always content-type-validate** if your app expects a specific type. `request.resource.contentType` reflects the upload's claimed type.

### Downloads — signed URLs preferred

For downloads of sensitive content, prefer **server-signed short-lived URLs** over `getDownloadURL()`:

```ts
const [signedUrl] = await bucket.file(path).getSignedUrl({
  action: "read",
  expires: Date.now() + 60 * 1000,    // 1 minute
});
```

The `getDownloadURL` token can be regenerated by deleting it via the Admin SDK, but it's a coarse revocation. Signed URLs expire and don't require revocation.

### `onObjectFinalized` for post-upload processing

```ts
import { onObjectFinalized } from "firebase-functions/v2/storage";

export const processUpload = onObjectFinalized(
  { bucket: "my-project.appspot.com", region: "us-central1" },
  async (event) => {
    const { bucket, name, contentType } = event.data;
    if (!contentType?.startsWith("image/")) return;
    // ...transcode, thumbnail, scan, extract EXIF, etc.
  }
);
```

Common post-upload tasks: virus scan, image resize/optimization, content moderation, metadata extraction, mirror to a CDN.

## Anti-patterns

- **`getDownloadURL()` for sensitive blobs** — long-lived public URL, hard to revoke. Use signed URLs with short expiry.
- **Trusting client-supplied filename / path** — sanitize. A client could write `../../etc/passwd`-shaped paths if your function naively uses the client's value.
- **Missing size cap in rules** — a client uploads 10GB; you pay.
- **Missing content-type validation** — a client uploads an executable named `pic.png`; downstream processing breaks or worse.
- **CORS not configured for the bucket** — client uploads fail with no useful error. Configure via `gsutil cors set`.

## Gotchas

- **CORS is bucket-level, not Firebase-Console-managed.** `gsutil cors set cors.json gs://my-bucket` is the path. Forgetting this is the most common Storage bug.
- **`getDownloadURL` tokens** are stored in the file's metadata; deleting the token via Admin SDK regenerates it (existing URLs break).
- **Bucket region** affects upload/download latency. Pick the bucket region near your users.
- **Storage rules size limit** — `request.resource.size` is in bytes; mind the math when comparing to MB.
- **Mobile resumable uploads** retry transparently — but a stalled upload counts toward storage quota until cleaned up.
