## What it is

D1 is Cloudflare's distributed SQLite-based database. Each database has a **primary region** (where writes go) and configurable **read replicas** globally. The [Sessions API](https://developers.cloudflare.com/d1/best-practices/read-replication/) provides read-your-writes consistency by tracking bookmarks across replicas. Real relational store with `JOIN`, `GROUP BY`, indexes, foreign keys, `EXPLAIN QUERY PLAN`, and 30-day time-travel restore.

Authoritative reference: [developers.cloudflare.com/d1](https://developers.cloudflare.com/d1/).

## When to use

- **New project, relational data, multi-region reads, under ~100GB** — D1 is the default.
- **Read-your-writes scenarios** — pair with the Sessions API.
- **Edge-native apps** — D1 lives on the Cloudflare network, bindings are first-class to Workers.
- **Audit trails, catalogs, users, orders** — typical relational shapes.

Don't use D1 when:

- **You need Postgres extensions** (PostGIS, pgvector, custom types) — use [Hyperdrive](/stacks/cloudflare/hyperdrive/) in front of Postgres.
- **Very-large datasets** beyond per-database limits — Hyperdrive'd external Postgres or sharded approach.
- **High-write append-only events** — use [Analytics Engine](/stacks/cloudflare/analytics-engine/) for time-series + [R2](/stacks/cloudflare/r2/) (via [Pipelines](/stacks/cloudflare/pipelines/)) for retention.
- **As a queue.** Don't `SELECT WHERE processed=0 LIMIT 1 FOR UPDATE` your way to a queue — use [Queues](/stacks/cloudflare/queues/).
- **Per-entity strong-consistency hotspots** — use [Durable Objects](/stacks/cloudflare/durable-objects/) SQLite per entity.

## 2025-2026 currency anchors

- **D1 GA'd in 2024.** Replication + Sessions API in 2025. Per-database size grew through 2025-2026; check current limits before designing.
- **Time-travel restore** built-in, 30 days, free — disaster recovery is included within that window.
- **Indexes, foreign keys, `EXPLAIN QUERY PLAN`** all work. D1 is a real relational store, not a toy.
- **Don't build D1 apps that assume a single primary location.** Reads come from replicas; writes round-trip to primary; Sessions API handles read-your-writes.

## D1 vs DO SQLite

| Property | D1 | DO SQLite |
|----------|----|-----------|
| Scope | Global (single DB shared by many Workers) | Per-DO instance |
| Consistency | Read-your-writes via Sessions API; eventual on replicas otherwise | Strong (single-writer per DO instance) |
| Transactions | Single-statement and batch | Full SQLite, multi-statement |
| Migrations | Wrangler migrations command | Code-managed (DDL in DO `constructor`) |
| Cross-row queries | Yes (full SQL) | Yes within the DO; no across DOs |
| Cross-tenant queries | Yes | No |
| Use when | Shared catalog, users, orders, analytics | Per-room state, per-user wallets, per-doc collab, per-tenant isolation |

D1 for the catalog. [DO](/stacks/cloudflare/durable-objects/) for per-entity strong consistency. Often both in the same app.

## Patterns

### Migrations

```bash
wrangler d1 create my-db
wrangler d1 migrations create my-db init
```

```sql
-- migrations/0001_init.sql
CREATE TABLE IF NOT EXISTS users (
  id TEXT PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  created_at INTEGER NOT NULL DEFAULT (unixepoch())
);

CREATE INDEX IF NOT EXISTS idx_users_email ON users(email);

CREATE TABLE IF NOT EXISTS orders (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  total_cents INTEGER NOT NULL,
  status TEXT NOT NULL CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled')),
  created_at INTEGER NOT NULL DEFAULT (unixepoch())
);

CREATE INDEX IF NOT EXISTS idx_orders_user_id ON orders(user_id);
CREATE INDEX IF NOT EXISTS idx_orders_status_created ON orders(status, created_at);
```

```bash
wrangler d1 migrations apply my-db          # local
wrangler d1 migrations apply my-db --remote  # production
```

Migrations are forward-only by default. **Make them idempotent** (`IF NOT EXISTS`). Test against a copy of prod data before applying to prod.

### Sessions API for read-your-writes

```ts
async function withSession<T>(req: Request, env: Env, fn: (s: D1DatabaseSession) => Promise<T>) {
  const bookmark = req.headers.get("X-Bookmark") ?? "first-unconstrained";
  const session = env.DB.withSession(bookmark);
  const result = await fn(session);
  return { result, bookmark: session.getBookmark() };
}

export default {
  async fetch(req, env) {
    const { result, bookmark } = await withSession(req, env, async (db) => {
      // db.prepare(), db.batch(), db.exec()
    });
    return Response.json(result, {
      headers: bookmark ? { "X-Bookmark": bookmark } : {}
    });
  }
}
```

The bookmark is opaque. Persist per-user (cookie, JWT claim, header); pass on subsequent requests. Pattern as middleware — don't hand-roll in every handler.

### Batch prepared statements

```ts
// Bad: per-iteration queries (counts against subrequests)
for (const item of items) {
  await env.DB.prepare("INSERT INTO orders (id, total) VALUES (?, ?)").bind(item.id, item.total).run();
}

// Good: batch
await env.DB.batch(items.map(item =>
  env.DB.prepare("INSERT INTO orders (id, total) VALUES (?, ?)").bind(item.id, item.total)
));
```

D1 batch is a single subrequest. Use for any multi-statement work — the latency win is real and helps the subrequest budget.

### Indexes for hot queries

```sql
-- Hot query: list user's orders by status, newest first
SELECT * FROM orders WHERE user_id = ? AND status = 'pending' ORDER BY created_at DESC LIMIT 20;

-- Right index: composite (user_id, status, created_at DESC)
CREATE INDEX idx_orders_user_status_ts ON orders(user_id, status, created_at DESC);
```

Use `EXPLAIN QUERY PLAN` to confirm the index is used. SQLite is a good citizen — it'll use an index if you have one, but you have to have the right one.

### Drizzle ORM

```ts
import { drizzle } from "drizzle-orm/d1";
import * as schema from "./schema";

const db = drizzle(env.DB, { schema });
const users = await db.query.users.findMany({ where: eq(schema.users.email, email) });
```

Drizzle is the most-used D1 ORM. Type-safe queries, schema migrations via `drizzle-kit`. Recommended over hand-writing every query for non-trivial schemas.

## Anti-patterns

- **D1 as a queue.** Race conditions, hot indexes, hot rows. Use [Queues](/stacks/cloudflare/queues/).
- **D1 without indexes.** Will table-scan happily; tens of ms at 100K rows, broken at 10M. Add indexes for hot queries from day one.
- **Forgetting Sessions API on read-after-write flows.** Write a row, redirect, fail to find the row, render a 404. Real bug.
- **Storing high-write append-only event data in D1.** Use Analytics Engine or Pipelines → R2.
- **Assuming D1 is multi-primary.** It's primary + replicas. Writes round-trip.

## Gotchas

1. **D1 reads from replicas by default** once replication is enabled. Without Sessions API, you can read a stale row right after writing it.
2. **Migrations are forward-only by default** — design for forward migrations, test against prod-shaped data.
3. **Subrequest budget applies** — each D1 query is a subrequest. Batch.
4. **`wrangler d1 execute --remote`** hits production; without `--remote` it hits local. Double-check before destructive operations.
5. **Time-travel restore is 30 days, included.** Verify it's enough for your RPO; pair with `wrangler d1 export` cron + R2 for longer retention.
