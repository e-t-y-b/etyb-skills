## What it is

**Continuous Native Generation (CNG)** is the Expo workflow contract:

- `ios/` and `android/` are in `.gitignore` — they're build artifacts, not source.
- `app.json` (or `app.config.js` / `app.config.ts`) is the source of truth.
- Native dependencies are declared via `plugins` in `app.json`.
- `npx expo prebuild` regenerates `ios/` + `android/` deterministically.
- EAS Build runs `expo prebuild` automatically before building.

The opposite is the **bare workflow** — `ios/` and `android/` committed, treated as source, modified by hand. CNG is the default for new Expo projects since SDK 50.

Canonical surface: [Continuous Native Generation](https://docs.expo.dev/workflow/continuous-native-generation/).

## When to use

For **any new Expo project**. The bare workflow is the escape hatch — used when:

- Brownfield: existing native iOS/Android app embedding RN
- Custom RN fork with modifications no config plugin expresses
- Third-party SDK that demands manual native edits and offers no config plugin

If you propose bare, *defend it*. CNG is the path that scales.

## 2025-2026 currency anchors

- **Default since SDK 50**.
- **EAS Build runs `expo prebuild` automatically** before each cloud build — you never check in the generated native projects.
- **`expo prebuild --clean`** blows away existing `ios/` and `android/` and regenerates from scratch.
- **`expo prebuild --platform ios`** regenerates one platform at a time.
- **`expo prebuild --no-install`** skips `npm install` / `pod install` — useful for inspection.
- **Config plugin contract is stable**; new mod hooks added per SDK.

## Patterns + anti-patterns

### Pattern: `.gitignore` includes native projects

```
# .gitignore
ios/
android/
```

If your repo *has* `ios/` and `android/` committed, you're in the bare workflow whether you meant to be or not.

### Pattern: Config plugin for every native edit

Need to add a key to Info.plist? Write a config plugin:

```js
// plugins/with-microphone-usage.js
const { withInfoPlist, createRunOncePlugin } = require('expo/config-plugins');

const withMicrophoneUsage = (config) =>
  withInfoPlist(config, (cfg) => {
    cfg.modResults.NSMicrophoneUsageDescription =
      'We use your microphone to record voice notes.';
    return cfg;
  });

module.exports = createRunOncePlugin(withMicrophoneUsage, 'with-microphone-usage', '1.0.0');
```

In `app.json`:

```json
"plugins": [["./plugins/with-microphone-usage"]]
```

Run `npx expo prebuild --clean` to regenerate native projects with the plugin applied. **Commit the plugin, not the regenerated native projects.**

### Pattern: `expo-build-properties` for build-level config

Don't write a custom plugin for things `expo-build-properties` already handles (Kotlin version, iOS deployment target, Android SDK levels):

```json
"plugins": [
  [
    "expo-build-properties",
    {
      "ios": { "deploymentTarget": "15.1" },
      "android": { "kotlinVersion": "1.9.0", "minSdkVersion": 24 }
    }
  ]
]
```

### Anti-pattern: "I just edited Info.plist directly"

```bash
# In Xcode: clicked the +, added NSCameraUsageDescription, saved
git add ios/MyApp/Info.plist  # 👈 BAD
```

Regenerated and lost on next prebuild. Write a config plugin.

### Anti-pattern: "I committed `ios/` because of one file"

Bare workflow choice with real cost — you now own all native upgrades, plugin compatibility, codegen, etc., manually. If it's truly one file, the plugin is faster to write than living with bare.

### Anti-pattern: Editing `Podfile` directly

```bash
# Adding `pod 'CustomLib'` by hand in ios/Podfile  👈 BAD
```

Use `withPodfile` mod or accept the bare workflow consequences. Manual Podfile edits are erased on `expo prebuild`.

## Gotchas

- **`expo prebuild` is destructive** — it regenerates native projects from scratch. Local Xcode/Android Studio config (signing certs, custom build settings) is discarded if not expressed in config plugins.
- **Pod install + Gradle sync** happen after prebuild — for slow networks, expect 1-5 min on first run.
- **Custom font assets / native asset additions** need plugin mods (`withAssetFiles`) or asset-config in `app.json`'s `assetBundlePatterns`.
- **`metro.config.js` is *not* regenerated by prebuild** — it's source code; commit it.
- **`eas.json` is source** — committed; not regenerated.
- **Order of plugins matters** — earlier plugins run first; later plugins see their changes. List order in `app.json` is execution order.
