## What it is

AlloyDB is PostgreSQL-compatible with separate compute and storage layers — 4x faster transactions than vanilla Postgres, 100x faster analytical queries via the columnar engine, and **AlloyDB AI** for in-engine vector embeddings via Vertex AI.

It's the modern Postgres on GCP. Position between [Cloud SQL](/stacks/gcp/cloud-sql/) (cheaper, sufficient for standard workloads) and [Spanner](/stacks/gcp/spanner/) (global ACID, horizontal scale).

Authoritative reference: [cloud.google.com/alloydb/docs](https://cloud.google.com/alloydb/docs).

## When to use

Pick AlloyDB when:
- Postgres workload exists and you need higher perf than Cloud SQL
- Analytical queries (joins, aggregations over millions of rows) are unacceptable on Cloud SQL — columnar engine delivers
- You want in-engine vector search (pgvector) with server-side Vertex AI embedding generation
- You need separate compute and storage scaling (horizontal read replicas)
- You're hitting the 128 vCPU Cloud SQL ceiling

Don't pick AlloyDB when:
- Workload is small/medium and Cloud SQL handles it — AlloyDB costs more at small scale; **don't pick newer reflexively**
- You need global ACID — use [Spanner](/stacks/gcp/spanner/)
- The vector store is the only need and you have >10M vectors with low-latency demands — use [Vertex AI Vector Search](/stacks/gcp/vertex-ai/)

## 2025-2026 currency anchors

- **AlloyDB AI** (2024-2025) — `google_ml_integration` extension + `embedding()` SQL function powered by Vertex AI text-embedding models; pgvector for vector ops; `google_ml.predict_row(...)` for arbitrary model invocation from SQL.
- **Columnar engine** — in-memory columnar representation of selected tables; 100x speedup on analytical queries; transparently used by query optimizer.
- **Read pool instances** (Preview) — horizontally autoscaling read replicas.
- **Cross-region replication** — async for analytical replicas; primary-DR pattern for transactional.
- **Index Advisor** — per-query index recommendations.

## Patterns

### Generate embeddings + vector search in SQL

```sql
CREATE EXTENSION IF NOT EXISTS google_ml_integration CASCADE;
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE products (
  id UUID PRIMARY KEY,
  name TEXT,
  description TEXT,
  embedding vector(768)
);

-- Embedding generated by Vertex AI text-embedding-005 via AlloyDB AI
INSERT INTO products (id, name, description, embedding)
VALUES (
  gen_random_uuid(),
  'Widget',
  'A useful widget',
  embedding('text-embedding-005', 'A useful widget')
);

-- Vector similarity search
SELECT id, name,
       embedding <=> embedding('text-embedding-005', 'gadget') AS distance
FROM products
ORDER BY embedding <=> embedding('text-embedding-005', 'gadget')
LIMIT 10;
```

No separate Pinecone/Weaviate/Qdrant for most workloads. Single store, single transaction boundary.

### Columnar engine

The optimizer transparently uses columnar representations when beneficial. To force a column-eligible table into columnar memory:

```sql
SELECT google_columnar_engine_add('products', 'embedding,price,category');
```

Analytical queries (`GROUP BY`, large `JOIN`s, range scans) get 10-100x speedups.

### Production cluster

```bash
gcloud alloydb clusters create prod-cluster \
  --region=us-central1 \
  --password=$(gcloud secrets versions access latest --secret=alloydb-root) \
  --network=projects/proj/global/networks/prod-vpc \
  --kms-key=projects/proj/locations/us-central1/keyRings/prod/cryptoKeys/alloydb

gcloud alloydb instances create prod-primary \
  --cluster=prod-cluster \
  --region=us-central1 \
  --instance-type=PRIMARY \
  --cpu-count=4 \
  --availability-type=REGIONAL
```

## Anti-patterns

- **AlloyDB just because it's newer** — Cloud SQL Enterprise Plus is excellent for the broad Postgres workload class and cheaper at small/medium scale.
- **Pinecone / Weaviate on GCP** when AlloyDB AI handles the volume — extra hop, extra cost.
- **No CMEK on regulated AlloyDB clusters** — audit finding.
- **Treating AlloyDB columnar engine as automatic** — verify with EXPLAIN that the optimizer is using it for your hot queries.
- **Cross-region replica without RPO/RTO documentation** — DR posture without a target is unprovable.

## Gotchas

- **Postgres extension set** is broader than Cloud SQL but still bounded — verify your required extensions.
- **Columnar engine memory** comes out of the instance memory pool — size accordingly.
- **AlloyDB Auth Proxy** is the legacy connectivity pattern; **Private Service Connect** is the 2026 preferred path.
- **Backups** are continuous; PITR with configurable window.
